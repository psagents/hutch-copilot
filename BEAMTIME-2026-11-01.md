## 2. Bridge fallback (`bridge-fallback`)

The fallback is a decision rule, not new code: `run` failing (rc 4, a timeout, or an action
that needs the live session's state) → `ping` → `exec`. Write it into `take-run/SKILL.md` on
this branch once Sunday confirms the triggers.

- [ ] `hutch-py --hutch mfx ping` → `offline` (as of today: nothing on :9999).
- [ ] Operator, in **their** mfxpython session:
      `exec(open('<checkout>/scripts/oc_bridge.py').read())` → "listening on port 9999".
- [ ] `ping` → `live`. `exec 'print(len(globals()))'` → same count as `run`.
- [ ] Same version probe as 0b through `exec`: `sys.prefix`, hutch_python, pcdsdevices. A
      mismatch with `run` is the strongest reason to use the bridge.
- [ ] Gate parity: `exec 'mfx_stopper_1.remove()'` → rc 5, same as `run`.
- [ ] One write through `exec --confirm write` (e.g. a short `autorun`), with the operator's OK.
- [ ] Latency: `exec` vs `run` for the same read. That is the case for keeping the bridge.
- [ ] **Stop the listener when done.** :9999 has no access control; any local user can exec
      in that namespace. Only leave it up while someone is at the console.
- [ ] Bridge dies with the session: close mfxpython → `ping` → `offline`, rc 4 on `exec`.
