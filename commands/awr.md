# /awr — Are We Ready (Beampath Status)

Triggered by: `/awr`, "are we ready", "is beam blocked", "beampath status",
"why don't we see beam", "what's blocking the beam", "awr {hutch}".

This command checks the LCLS beampath for the given hutch — querying which lightpath
devices are inserted, removed, or transmitting — and reports what may be blocking
beam delivery. All checks are **read-only**.

---

## Phase 1: Identify Hutch

Pull from session state. If not in state, ask once: "Which hutch? (e.g. mfx, tmo, rix)"

---

## Phase 2: Generate the AWR Script

Build a Python script that uses the `lightpath` package (preferred) or `happi` (fallback)
to query all beampath devices. The script runs through the hutch-python bridge where
these packages are available.

### Preferred: lightpath-based script

```python
# awr_{hutch}.py — Are We Ready check
# Generated by beam-opr; runs in hutch-python environment via bridge

import lightpath
from lightpath import LightController

# Build the lightpath controller for this hutch
lc = LightController('{hutch}')

# Get all devices in the beam path
devices = lc.devices

results = []
for device in devices:
    try:
        name = device.name
        prefix = device.prefix
        
        # Transmission
        try:
            trans = device.transmission
        except AttributeError:
            trans = None
        
        # Inserted/removed state
        try:
            inserted = device.inserted
            removed  = device.removed
        except AttributeError:
            inserted = None
            removed  = None
        
        if inserted is True:
            state = "IN-BEAM"
        elif removed is True:
            state = "OUT"
        elif trans is not None:
            state = f"T={trans:.1%}"
        else:
            state = "UNKNOWN"
        
        results.append((name, state, prefix))
    except Exception as e:
        results.append((device.name, f"ERROR: {e}", ""))

# Print table
print(f"AWR Report — {'{hutch}'.upper()} — " + __import__('datetime').datetime.now().strftime('%Y-%m-%d %H:%M'))
print(f"{'Device':<35} {'State':<15} {'PV Prefix'}")
print("-" * 80)
for name, state, prefix in results:
    flag = "  ←← BLOCKING?" if state == "IN-BEAM" else ""
    print(f"{name:<35} {state:<15} {prefix}{flag}")
```

### Fallback: happi-based script (if lightpath not available)

```python
# happi fallback
import happi
from happi.loader import from_container

client = happi.Client.from_config()

# Search for all devices on this beamline
results_raw = client.search(beamline='{hutch}'.upper())
results = []
for item in results_raw:
    try:
        dev = from_container(item)
        dev.wait_for_connection(timeout=1.0)
        if hasattr(dev, 'inserted'):
            state = "IN-BEAM" if dev.inserted.get() else ("OUT" if dev.removed.get() else "UNKNOWN")
        else:
            state = "N/A"
        results.append((item.name, state, item.prefix))
    except Exception as e:
        results.append((item.name, f"ERROR", ""))

print(f"AWR Report — {'{hutch}'.upper()}")
print(f"{'Device':<35} {'State':<15} {'PV Prefix'}")
print("-" * 70)
for name, state, prefix in results:
    flag = "  ←← BLOCKING?" if state == "IN-BEAM" else ""
    print(f"{name:<35} {state:<15} {prefix}{flag}")
```

Save the script to a temp file and run it via the bridge:

```python

```

Or pass the script content directly as a multi-line code block to the bridge.

If the bridge is not connected, provide the script for the user to run manually in
their hutch-python session.

## Phase 4: Parse and Report

Parse the raw output into a structured report. Highlight:

1. **Devices IN-BEAM** — may be blocking if not expected
2. **Devices with T=0%** — full attenuators, closed apertures
3. **ERROR devices** — could not be queried (possible PV communication issue)
4. **Devices with low transmission** — attenuators at partial insertion

**Formatted report:**

```
AWR Report — MFX — 2026-06-25 14:32
══════════════════════════════════════════════════════════
POTENTIAL BLOCKERS (inserted / T=0):
  mfx_stopper_1       IN-BEAM    MFX:PPS:MMS:ST1
  mfx_att_1           T=0.0%     MFX:ATT:COM:A1

IN BEAM (expected):
  mfx_lens_1          IN-BEAM    MFX:MMS:LENS:1

OUT of beam (OK):
  mfx_target          OUT        MFX:MMS:TGT

Transmission summary: 0% (stopper in, attenuator at 0%)
══════════════════════════════════════════════════════════
Beam is blocked. Check: mfx_stopper_1 (state: IN-BEAM).
```

---

## Phase 5: Diagnose

Interpret the results:

- If a **stopper or MPS device** is IN-BEAM: this is likely a hard block — must be
  resolved by the operator with appropriate authorization.
- If an **attenuator** is at T=0%: check if it's intentional (protection) or a misconfiguration.
- If a **diagnostic** is IN-BEAM: normal (most diagnostics are non-intercepting or thin foils).
- If the report shows all devices OUT and T~100% but beam is still not visible:
  check machine-level PVs (see `references/beam-status-pvs.md`).

---

## Known Limitations

- Device classification (blocking vs. diagnostic) may not be perfect — human judgment is needed.
- `lightpath` may not have an entry for every hutch.
- Devices that are in maintenance or disconnected will show as `ERROR`.
- This is a point-in-time snapshot — states can change rapidly.

Always cross-reference with the hutch operator before moving any device.
